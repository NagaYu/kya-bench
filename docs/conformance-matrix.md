# Conformance matrix: KYA Bench vs reference implementations

How KYA Bench's expected verdicts compare with what each protocol's own reference
implementation does on the same vectors. Generated by `tools/matrix/run_matrix.py`;
do not edit by hand.

## Reproduce

The matrix needs the reference implementations, so it is **not** part of `tools/ci.sh`.
Everything below runs offline once the clones and dependencies are in place.

```bash
mkdir -p ../kya-refs && cd ../kya-refs
git clone https://github.com/agent-intent/verifiable-intent && git -C verifiable-intent checkout 356c29635f1c44df7de02edb58699ca9f29bece6
git clone https://github.com/google-agentic-commerce/AP2 && git -C AP2 checkout e1ea56db72a6385bce3e5c1112b3a56ce60acb43
git clone https://github.com/visa/trusted-agent-protocol && git -C trusted-agent-protocol checkout 16d59bdf3f8a542bc538d0962edbb80ea30a02af
cd -
python3 -m venv .matrix-venv
.matrix-venv/bin/pip install "cryptography==46.0.5" "jwcrypto==1.5.6" "pydantic==2.12.5" "sd-jwt==0.10.4"
.matrix-venv/bin/python tools/matrix/run_matrix.py --refs ../kya-refs && python3 tools/matrix/render.py
```

Node.js (tested with 22) runs the TAP reference proxy. `run_matrix.py` refuses to run if
a clone is not at its pinned commit. No npm install is needed: the harness stubs the
proxy's express/axios/dotenv imports and calls its `verifySignature` directly.

## How to read it

- **agree**: the reference reaches KYA's expected verdict. **incidental** agreements are
  rejections the reference made for a different, early reason (see VI-M1, TAP-M1): same
  verdict, different cause.
- **diverge / verdict**: KYA expects accept or reject and the reference does the opposite.
- **diverge / spec_gap**: KYA expects `indeterminate` (the spec leaves the case undefined)
  and the reference decides. These show how the reference resolves each gap.
- **not_runnable**: the vector cannot be expressed in the reference's input model. Counted,
  with reasons, rather than forced through.
- A reference exception counts as a rejection; the raw outcome is kept in the JSON.

## Findings

### VI-M1: Reference rejects when L1 card_id differs from payment_instrument.id

- **Reference:** verification/chain.py step '4c-bis' (commented 'Optional card_id cross-check (SHOULD-level)') returns an error whenever L1 carries card_id and it differs from the mandate's payment_instrument.id.
- **Spec:** credential-format.md §3.3: card_id is OPTIONAL, an 'Opaque card-level identifier assigned by the Issuer'; payment_instrument.id is an 'Instrument instance identifier (e.g., a token UUID)' (§4.4.2). No section requires them to be equal, and the spec's own examples use card_id 'card-mc-8842' (§3.6) with payment_instrument.id 'f199c3dd-…' (§11).
- **Assessment:** KYA follows the text. The reference enforces an unwritten binding as a hard failure despite its own 'SHOULD-level' comment. Not a KYA bug; candidate note for the VI Issue.
- **Vectors (5):** `autonomous-l2-only`, `autonomous-multi-pair`, `autonomous-valid`, `budget-cumulative-within`, `immediate-valid`

### TAP-M1: Reference only reads the camel-case keyId parameter

- **Reference:** cdn-proxy/server.js parseRFC9421SignatureInput returns attributes.keyId; with RFC 9421 'keyid' it is undefined, validateKeyId fails and the request is rejected with 'Invalid Key ID Format' before any other check.
- **Spec:** RFC 9421 §2.3 and the Visa merchant specification page use 'keyid'; RFC 8941 keys are lower-case only. The repo's own merchant-backend verifier also expects 'keyid'. See spec gap TAP-02.
- **Assessment:** KYA follows RFC 9421 and the Visa page; the reference proxy and agent agree with each other but not with either. Every RFC-spelled TAP vector is rejected for this one reason, so TAP agreements on reject vectors are incidental.
- **Vectors (7):** `tap-browse-ed25519-valid`, `tap-content-digest-covered-valid`, `tap-cro-id-token-forged`, `tap-cro-nonce-mismatch`, `tap-cro-valid`, `tap-nonce-reused-by-other-key`, `tap-payment-rsa-pss-valid`

### TAP-M2: Reference accepts the keyId spelling that KYA leaves undefined

- **Reference:** The reference agent emits keyId and the proxy accepts it.
- **Spec:** Spec gap TAP-02: repo (keyId) vs RFC 9421 / Visa page (keyid).
- **Assessment:** Expected: the reference resolves the gap in favour of its own spelling. Confirms TAP-02 is a real interoperability split rather than a theoretical one.
- **Vectors (1):** `tap-repo-keyId-parameter`

### AP2-M1: SDK verifies a checkout mandate presented without a payment mandate

- **Reference:** MandateClient.verify works per chain; the adapter (like the merchant sample) verifies whatever chains are presented.
- **Spec:** specification.md Modes: 'Verifiers of Mandates always receive a closed Payment and Checkout Mandate, regardless of the mode.' Verification rules are per role (Merchant: checkout; Credential Provider/Network: payment).
- **Assessment:** Both readings are defensible: KYA, as a neutral whole-transaction verifier, applies the 'always receive both' sentence; a single-role verifier legitimately sees one chain. Recorded as a scoping difference, not a bug on either side.
- **Vectors (1):** `ap2-payment-mandate-missing`

### AP2-G: SDK decides cases KYA leaves undefined

- **Reference:** AP2-01 cart total vs amount: not compared (accept). AP2-02 mixed flows: accept. AP2-04 decimal max 250.0: treated as minor units (reject). AP2-05 recurrence period: SDK's own period arithmetic (accept). AP2-06 budget: major units, max x 100 (accept). AP2-07 'product' line items: UCP schema validation fails (reject). AP2-08 no revealed acceptable_items: wildcard (accept).
- **Spec:** See docs/spec-gaps.md AP2-01..AP2-08: in each case the docs are silent or contradict the schema/SDK.
- **Assessment:** These are the reference's choices where the text does not decide. AP2-04 and AP2-06 together show the unit problem: the SDK reads amount_range.max as minor units but budget.max as major units.
- **Vectors (7):** `ap2-acceptable-items-undisclosed`, `ap2-amount-range-decimal-max`, `ap2-budget-unit-ambiguous`, `ap2-cart-total-mismatch`, `ap2-line-item-product-shape`, `ap2-mixed-flows`, `ap2-recurrence-period-undefined`

### AP2-O1: Observation: the SDK's checkout chain does not recompute checkout_hash on its own

- **Reference:** CheckoutMandateChain.verify compares checkout_hash only with a caller-supplied expected_checkout_hash; ap2-checkout-hash-mismatch is rejected through the payment chain's transaction_id comparison instead.
- **Spec:** specification.md Merchant verification: 'Verify that the hash of the Checkout JWT sent for approval matches the value included for the checkout_hash claim.'
- **Assessment:** Same verdict here, but a merchant that verifies only the checkout chain must recompute the hash itself. Not a divergence; noted for implementers.

### VI-G: Spec-gap vectors masked by the card_id check

- **Reference:** Rejected by VI-M1 before the gap-relevant logic runs.
- **Spec:** G-02, G-03, G-05.
- **Assessment:** No information about the reference's handling of these gaps; recorded for completeness.
- **Vectors (3):** `budget-without-network-state`, `gap-g02-checkout-jwt-without-merchant-id`, `gap-g03-line-items-sku-shape`

### TAP-G: Spec-gap vectors masked by the keyId check

- **Reference:** Rejected by TAP-M1 before tag or payment-container handling.
- **Spec:** TAP-01, TAP-03. The reference implements neither the payment container nor a tag/operation check.
- **Assessment:** No information beyond TAP-M1.
- **Vectors (2):** `tap-apc-signature-undefined`, `tap-payer-tag-on-browse`
